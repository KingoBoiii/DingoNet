# DingoNet v0.2 whole-release review

**Scope**: `git diff master...HEAD` on `feat/v0.2-structure` (master `ef66b46`), three commits: `b476b2a` message
registry, `53bb61b` session epochs, `059cc85` mirror toolkit. `include/DingoNet/{Messages,Session,Mirror}.h`,
`src/{Messages,Session,SessionMessages}.cpp`, `src/SessionMessages.h`, `tests/{MessageTests,EpochTests,MirrorTests,
SessionTests}.cpp`, the `CLAUDE.md` and plan diffs. Wire bytes compared against master's and v0.1.0's (`b815b9e`)
encoders. Focus: the epoch wire (`Epoch` F8, `Stamped` F9), the `Welcome`/`SeatLeft` changes and
`k_SessionProtocol` 2, v0.1 compatibility, the registry, the mirror, portability, docs.

**Baseline**: clean GCC 13 Debug and Release builds (`-Wall -Wextra -Werror`), 135/135, about 0.6 s. MSVC could not
be run here. Probes in a scratchpad copy: `probe1.cpp` (two `Session`s with epochs over Loopback on a fake clock and
over TCP on `127.0.0.1`: a reliable message sent just before `BeginEpoch`, `MaxUnreliablePayload()` before `Start`,
events and messages of one `Update`), `probe2.cpp`/`probe3.cpp` (`RenderClock` fed 20 Hz wall-clock stamps at 60 fps:
a 0.8 s network stall with its backlog delivered in one frame or over three, both call orders, one stamp 0.6 s late,
`Settle` after a gap), `probe4.cpp` (a v0.1 exhaustive `switch` on `Event::Kind`), `probe5.cpp`/`probe6.cpp` (every
new public header under `<Windows.h>`-style `min`/`max`/`near`/`far`/`SendMessage`/`ERROR` macros, and the typed
`Send`/`Broadcast`, `Encode`, `MessageRouter`, `Tracks<int, {double, float wrapper, int}>`, `Timeline`, `EventQueue`
and `RenderClock` instantiated under GCC 13 and clang 18 with `-Wall -Wextra -Werror -Wconversion`).

**Verdict**: no High. The wire, the compatibility story and the registry are sound. Fix F1 (a documented order and a
test) and the release items in F7 before tagging `v0.2.0`; the rest are Low and can ship as documented behaviour.

Findings: 0 High, 1 Medium, 6 Low.

## F1 — Medium — A state-change message sent just before `BeginEpoch` is dropped on every client
`src/Session.cpp:574-592` (`OnEpoch`), `src/Session.cpp:594-613` (`DropQueuedGameMessages`, `BeginEpoch`),
`include/DingoNet/Session.h:152-157`, `CLAUDE.md:80`, plan Phase 5 ("`BeginEpoch()` at `RunStart`, `RunOver` and back
to the lobby")

Scenario: the host detects Game Over and does the natural thing: `Broadcast(RunOver{...})`, then `BeginEpoch()`. Both
go out in the same flush: `RunOver` stamped with the old epoch, then `Epoch`. Each client's next `Poll` brings both;
`OnGamePacket` queues `RunOver` (its stamp still matches), then `OnEpoch` calls `DropQueuedGameMessages`, which clears
it. `Broadcast` returned the seat count, so the host believes it was delivered. If the two are sent a frame or more
apart, the outcome depends on whether a client's `Update` and `TakeMessages` happen to fall between their arrivals.
Wrong result: a reliable message is lost on every client, deterministically when sent in the same frame, by timing
otherwise. Verified by experiment: Loopback, `RunOver` then `BeginEpoch` with no client poll in between, 0/1
delivered; with one client `Update` + `TakeMessages` in between, 1/1; TCP, 0/20. The header's "every game message of
the old one still in flight is dropped wherever it lands" does not tell the game that this includes messages that
already arrived but were not taken yet, nor which order to use. The same applies to a host's own queue: messages a
client sent before it saw the new epoch are dropped too (intended by the plan).
Fix: document the order in `Session.h` and `CLAUDE.md` ("call `BeginEpoch()` first, then send the new state's
messages, such as `RunOver`, which travel in the new epoch") and that an old epoch's message already received but not
yet taken is dropped too. Add an `EpochTests` case pinning "`BeginEpoch` then a reliable message: delivered once,
after `EpochChanged`". If the game must be able to send a last old-epoch message, the alternative is to stop clearing
the client's queue at `Epoch` and give `Message` an `Epoch` field instead.
Status: documented and pinned. `BeginEpoch()` in `Session.h` and the Session entry in `CLAUDE.md` now say: call it first, then send the new state's messages (a `RunOver` that must arrive goes after it); one sent before may be dropped, including one already received but not yet taken. Test `EpochMessageSentBeforeBeginEpochIsDroppedAndOneSentAfterIsDelivered` (lagged loopback).

## F2 — Low — `EpochChanged` and the new epoch's first messages come out of the same `Update`, in no stated order
`include/DingoNet/Session.h:147-150` (`TakeEvents`/`TakeMessages`), `CLAUDE.md:80-81`

Scenario: the host calls `BeginEpoch()` and sends the new run's first reliable message (a spawn list) in the same
frame. The client's next `Update` raises `EpochChanged` and queues the message. A game that drains `TakeMessages()`
first, applying the spawn list to its mirror, and then handles `TakeEvents()` by clearing its `Tracks`, `Timeline`
and `EventQueue` and resetting the `RenderClock` (as `Mirror.h` and `CLAUDE.md` tell it to) throws away the new run's
first state.
Wrong result: the first messages of each new epoch are lost to the game in that order. Verified by experiment: one
client `Update` gave 1 event (`EpochChanged`) and 1 message. Nothing in `Session.h` or `CLAUDE.md` says that events
must be taken before messages.
Fix: say so in `Session.h` beside `TakeEvents`/`TakeMessages` and in the `Mirror` paragraph ("handle `TakeEvents()`
before `TakeMessages()`: an `EpochChanged` comes before the new epoch's messages"), or give `Message` an `Epoch` field.
Status: documented and pinned. `TakeEvents` in `Session.h` and `CLAUDE.md` say events are taken before messages. Test `EpochTakingEventsBeforeMessagesKeepsTheNewEpochsFirstMessage`.

## F3 — Low — `MaxUnreliablePayload()` is 1100 before `StartHost`/`StartClient`, even with `Epochs = true`
`include/DingoNet/Session.h:69-72`, `include/DingoNet/Session.h:164`, `src/Session.cpp:151`

Scenario: a game builds its `Session` with `Epochs = true` at init and computes its snapshot room from
`MaxUnreliablePayload()` before starting (Headstone's room formula is a constant today; the plan says it "shrinks by
2"). `m_EpochsOn` is set only in `Start`, so the call returns 1100.
Wrong result: snapshot parts of 1099–1100 bytes are then refused with an error on every send. Verified by experiment:
`Session(Epochs = true).MaxUnreliablePayload()` before `StartHost` is 1100. The `Epochs` comment says a client's own
setting is "a hint for `MaxUnreliablePayload()` until then", which reads as covering this time too.
Fix: return the `m_Params.Epochs` answer when not started (`(m_Transport ? m_EpochsOn : m_Params.Epochs)`), or
document "valid after Start".
Status: fixed. `MaxUnreliablePayload()` reads `m_Params.Epochs` until a transport is set, then the adopted flag. Test `EpochMaxUnreliablePayloadFollowsTheParamsBeforeStart`.

## F4 — Low — `RenderClock` jumps render time back on network delay, not only on host stalls and restarts
`include/DingoNet/Mirror.h:77-86` (restart), `include/DingoNet/Mirror.h:92-97` (stall resync), `CLAUDE.md:81`

Scenario (a): the network stalls for 0.8 s (Wi-Fi hiccup, TCP retransmission) while the host keeps stamping with its
wall clock. `HostNow` keeps running through the gap, as designed. The backlog then arrives. Its first stamp is about
0.8 s behind `HostNow`, so `OnSnapshot` takes it for a host stall and resyncs render back to it. The later stamps
raise `HostNow` again, and the next `Advance` snaps render forward. If the whole backlog lands in one frame and the
game calls `OnSnapshot` for all of it before `Advance`, nothing shows. If the backlog spreads over frames, or the game
advances before reading its packets, the frames in between render 0.8 s in the past.
Scenario (b): one unreliable snapshot arrives more than `SnapError` behind the latest (reordered across a relay).
`OnSnapshot` restarts the clock on that single stamp: render goes back by the delay, `Restarts()` counts a host
restart that never happened, and the next normal stamp snaps render forward.
Wrong result: every interpolated entity jumps back and forth. Verified by experiment (60 fps, 20 Hz stamps):
- (a), backlog in one frame, `OnSnapshot` then `Advance`: largest step back 0.017 s.
- (a), backlog in one frame, `Advance` then `OnSnapshot`: largest step back 0.817 s.
- (a), backlog over three frames: largest step back 0.815 s.
- (b), one stamp 0.6 s late: `Restarts()` 1, a 0.599 s step back.

No test covers either case. `MirrorClockConvergesAfterAHostStall` resumes the stamps where they stopped, which is a
host whose clock paused.
Fix: decide on resyncs once per frame and only when they persist. Move the stall check into `Advance`, after the
frame's stamps, so a backlog that catches up doesn't trigger it, and act only if `HostNow` is still more than
`SnapError` ahead of the latest stamp after a short grace (for example, `Delay`). Restart only when a second stamp
confirms the jump back, or leave restarts to `Reset()`. A session with epochs already drops a previous run's
stragglers, and the docs already tell the game to `Reset()` at `EpochChanged`. Add the backlog-over-frames case and a
single late stamp to `MirrorTests`.
Status: fixed. `RenderClockParams` gains `RewindError` and `RestartError` (2.0 each). `OnSnapshot` no longer moves render time (`HostNow` may still resync down); `Advance` rewinds only when render is ahead of its target by more than `RewindError`, holds (rate 0) when ahead by more than the slew band, and a restart needs a stamp more than `RestartError` behind. Tests `MirrorClockNetworkStallBacklogNeverMovesRenderBack` (0.8 s stall, backlog over 1, 3 and 6 frames, both call orders), `MirrorClockSingleLateStampIsIgnored`, `MirrorClockHoldsThenCatchesUpWhenAheadOfTargetWithinRewindError`, `MirrorClockRewindsWhenFarAheadOfTarget`; `MirrorClockConvergesAfterAHostStall` and `MirrorClockRecoversAfterSettleAndSilence` unchanged and passing.

## F5 — Low — `Settle()` moves render time back when the last snapshot is older than `Delay`
`include/DingoNet/Mirror.h:115-119`, `include/DingoNet/Mirror.h:145-151`, `CLAUDE.md:81`

Scenario: snapshots pause for 0.5 s before the host's Game Over arrives (a lost final part, or a host that stops
snapshotting before it sends the result). Unsettled, render runs on past the latest stamp: it trails `HostNow` by
`Delay` and `HostNow` grows with the time since arrival. The game calls `Settle()`, and the next `Advance` sets
`m_Render = min(m_Render, m_Latest)`.
Wrong result: render time drops back to the last stamp. Extrapolated entities snap back to their last sampled
positions, and a `Timeline` step between the two times reverts. Verified by experiment: render went from 1.471 to
1.000 in one `Advance` after `Settle()`. `CLAUDE.md` says render time is "never decreasing" except for two named
cases and that `Settle()` makes render "move up to the latest stamp"; neither covers this.
Fix: hold at `(std::max)(m_Render, m_Latest)` while settled, or slew down at `MaxSlew`. Otherwise document it as a
third case. Add a test that settles after a gap.
Status: fixed. Settled, render moves forward to the latest stamp and stops, or holds if already past; `Mirror.h`, `CLAUDE.md` and the plan describe exactly that. Test `MirrorClockSettleAfterAGapHoldsRenderTime`.

## F6 — Low — The new `Event::Kind::EpochChanged` breaks a game's exhaustive `switch` under `-Werror`
`include/DingoNet/Session.h:96`, plan "v0.2 — Structure" ("All are opt-in, so a game on v0.1's API keeps compiling")

Scenario: a game switches over `Event::Kind` with one case per v0.1 kind and no `default` (the usual way to make the
compiler flag a new kind). With v0.2, `-Wswitch` (in `-Wall`) reports `EpochChanged` as not handled. A game built
with `fatalwarnings` on Linux, like Headstone, fails to build even with `Epochs = false`. MSVC's equivalents (C4061,
C4062) are off by default, so `/W4 /WX` builds are unaffected.
Wrong result: v0.1 source no longer builds on GCC or clang with `-Werror`. Verified by experiment: GCC 13 and clang 18
both fail with "enumeration value 'EpochChanged' not handled in switch".
Fix: call it out in the plan, the release notes and `CLAUDE.md` as the one source change of v0.2 ("add a case for
`EpochChanged`"). The enumerator itself is the right design.
Status: documented. The one source-compat note of v0.2, in the plan's Phase 2 As built, `CLAUDE.md`'s Session entry and beside `EpochChanged` in `Session.h`: a game's `switch` over `Event::Kind` needs a case or a `default`.

## Checked and correct
- Compatibility, both directions:
  - Master, v0.1.0 and v0.1.1 all check Hello's leading `u16` session protocol before anything else and send the
    unchanged `Reject` layout, so a v0.2 client at a v0.1 host gets `Rejected(ProtocolMismatch)` at once.
  - A v0.1 Hello at a v0.2 host gets `Reject(ProtocolMismatch)` and a hang-up.
  - Hello and Reject bytes are identical to master's encoders.
  - The new `SessionTests` pin both directions with hand-written v0.1 bytes.
- Wire, all strictly decoded:
  - `Welcome`: an epochs byte above 1 is malformed.
  - `SeatLeft`: the transport byte must be at most `Error`, and `Closed` unless the leave is `TransportLost`. The host
    always sends it that way (`VacateSeat`).
  - `Epoch`: exactly 2 bytes.
  - `Stamped`: at least 3 bytes, and a session id inside the stamp is malformed.
  - `k_SessionProtocol` is 2.
- Stamping rules:
  - A client stamps only once welcomed.
  - A host's `Broadcast` stamps once for every seat.
  - Unseated peers are never stamped to, and their raw packets still reach `UnseatedPacket`.
  - A `Stamped` from an unseated host peer is `Unexpected`.
  - Stale stamps are counted in `StaleDropped()` and never reach `Bad`, so they never count toward the 32-strike
    hang-up.
  - An unstamped game packet from a seated peer with epochs on is malformed and does count.
  - An empty send with epochs on is refused.
- Epoch races:
  - A new-epoch unreliable packet that overtakes its `Epoch` is dropped.
  - A `Welcome` sent before a `BeginEpoch` is followed by the `Epoch` on the same reliable channel, because the joiner
    is already seated on the host.
  - A late joiner gets the current epoch in its `Welcome`.
  - The `u8` wraps.
  - `BeginEpoch` also drops pending `LastMessages`. The F2 reseat path, `LastMessages` and the handshake trim are
    unchanged from v0.1.1.
- Steam: `Hello` is never stamped, so the transport's first-byte `0xF0` check still ends the 1 s ignore window. A
  stamped 1098-byte payload is exactly `MAX_UNRELIABLE_BYTES`.
- Unreliable limit:
  - `UnreliableFits` runs before stamping in the span and typed `Send`/`Broadcast`.
  - Typed sends check `FitsUnreliable` and the direction (open while not `Active`) and count `NoteSent` only for
    packets handed to the transport, once per `Broadcast` that reached a seat.
  - `EpochMaxUnreliablePayloadIs1098WithEpochsOn` pins 1098/1099 on both sides.
- Registry:
  - `IdOf` rejects ids outside 0–255 at compile time.
  - Reserved ids are refused by `Encode` and `On` at runtime.
  - `Dispatch` checks the direction, then decodes strictly (`Read`, `Ok()`, no trailing bytes), and counts
    `Received`/`BytesIn` only when a handler ran.
  - Handlers must be copyable (static_assert).
  - The heap table survives `On`/`Dispatch` from inside a handler.
  - The router is neither copyable nor movable.
  - `Name` is documented as `const char*`, with a hex fallback otherwise.
- Mirror:
  - `Tracks::Sample`: brackets, holds before the oldest sample, extrapolates past the newest with a capped
    `MinExtrapolateGap` span, then holds.
  - `Trim` keeps the bracket and forgets stale keys.
  - `Timeline::Trim` keeps the step in force, so `At` never goes empty after a trim (probe).
  - `EventQueue` keeps insertion order for equal times.
  - Non-finite times and dt are ignored, and dt is clamped.
- Portability:
  - Every `min`/`max`/`clamp`/`numeric_limits` call in the new headers is parenthesized.
  - No new public name collides with a `<Windows.h>` macro (probe5).
  - No `-Wchanges-meaning` hazard in the library's own headers.
  - The templates instantiate cleanly under GCC 13 and clang 18 with `-Wall -Wextra -Werror -Wconversion`, including
    `Tracks<int, int>` (probe6).
  - No platform header in a public header.
- Conventions:
  - `Dingo::Net`, `m_`/`s_`, `DN_`, tabs and new-line braces, `Internal::Log*` with `std::format`.
  - Comments stay within the rule: the few in `Mirror.h` and `Session.h` state constraints.
  - The suite has 135 tests, matching the plan's As-built count.

## R1 — Low — `Mirror.h`/`CLAUDE.md` still say `HostNow()` never decreases and render never passes it; the fix breaks both
`include/DingoNet/Mirror.h:96-99` (`OnSnapshot` resync down), `CLAUDE.md:81` (Mirror entry), plan Phase 3 As built

Scenario: a clock runs 1.5 s on a single stamp (10.0), then stamp 10.05 arrives (a host stall, or the first stamp of a network backlog). `Estimate - hostTime > SnapError` sets `m_Estimate = hostTime`, and render is no longer pulled back. Probe: before, render 11.417, `HostNow()` 11.500; after, render 11.417, `HostNow()` 10.050.
Wrong result: `HostNow()` decreases by 1.45 s and `RenderTime()` is 1.37 s past `HostNow()` until the target catches up. `CLAUDE.md` says `HostNow()` is "never decreasing" and `RenderTime()` "never past `HostNow()`", and in the same paragraph that `HostNow` "may still resync down", so the entry contradicts itself. A game that computes anything from `HostNow() - RenderTime()` (extrapolation budgets, an "age of view" HUD) gets a negative value. "The slew band" in the `RenderTime()` text is undefined (it is `MaxSlew * CatchUp`, 0.025 s).
Fix: state the exceptions: `HostNow()` can drop on a resync, and render can sit ahead of it while held. Give the band a number or a name. Alternatively keep `HostNow` from dropping and track the lowered target separately.
Status: fixed. `Mirror.h`, `CLAUDE.md` and the plan now say `HostNow()` can drop on a resync, `RenderTime()` can sit ahead of it while held, and the band is `MaxSlew * CatchUp` (0.025 s). Docs only.

## R2 — Low — `MaxUnreliablePayload()` and `EpochsOn()` disagree before `Start` and after `Stop` for a client whose adopted setting differs from its params
`include/DingoNet/Session.h:165,170`, `src/Session.cpp:151,198`

Scenario: a client built with `Epochs = false` joins an epochs host: `m_EpochsOn` becomes true from `Welcome`. After `Stop` or `Lost`, `Shutdown` resets `m_Transport` but leaves `m_EpochsOn`. `MaxUnreliablePayload()` then reads `m_Params.Epochs` (1100) while `EpochsOn()` says true. Before `Start`, `EpochsOn()` is false and `MaxUnreliablePayload()` follows the params (1098 with `Epochs = true`).
Wrong result: two accessors of one fact give different answers outside a started session. Harmless for sends (nothing is sent without a transport), but a game logging or sizing from the pair is confused. `EpochMaxUnreliablePayloadFollowsTheParamsBeforeStart` only covers a host whose params match.
Fix: derive both from one place (for example make `EpochsOn()` return the same expression), or document that both are meaningful only while started except `MaxUnreliablePayload()`'s pre-start answer.
Status: fixed. `m_EpochsOn` is reset to `m_Params.Epochs` in `SetParams` and `Shutdown`, so `EpochsOn()` and `MaxUnreliablePayload()` read one flag. Tests `EpochClientAfterStopFollowsItsOwnParamsAgain` and the extended `EpochMaxUnreliablePayloadFollowsTheParamsBeforeStart`.
