# DingoNet v0.3 whole-release review

**Scope**: `git diff v0.2.0...HEAD` on `feat/v0.3-lan-discovery` (HEAD `e912329`): phase 1 `Delivery::UnreliableSequenced`
and `IsUnreliable` (`Transport.h`, `Messages.h`, `Session.{h,cpp}`, `SendLimits.h`, `SteamTransport.cpp`, the
`Conditioner`'s per-peer sequencing), phase 2 `UdpTransport` on the bundled ENet 1.3.18 (`include/DingoNet/UdpTransport.h`,
`src/Platform/UdpTransport.cpp`, `src/Platform/EnetLink.h`, `src/Internal/UdpTestAccess.h`, premake, the package
scripts' `THIRD_PARTY.txt`), phase 3 LAN discovery (`5f65770`, `e912329`: `include/DingoNet/LanDiscovery.h`,
`src/LanDiscovery.cpp`, the new `Socket.h` UDP calls in `WinSocket.cpp`/`PosixSocket.cpp`), `docs/transports.md`,
`docs/discovery.md`, `CLAUDE.md` and the plan's v0.3 section. Focus: `UdpTransport` against the `Transport` contract
(event order, `Disconnect`/`Close`, caps, floods, memory), ENet error paths, the sequenced guarantee, Windows vs
Linux, the discovery wire, amplification and rate limits, public-header portability, `-Werror` hazards, leaks.

**Baseline**: static review against the vendored ENet 1.3.18 source (`vendor/enet/{protocol,peer,host,win32,unix}.c`).
Builds and tests were not run by this review. Known and accepted, not repeated here: phase 2 review findings 2, 5 and
6 (Low), and that the LAN list can be spoofed on a LAN.

**Verdict**: one High. The sequenced guarantee holds (ENet sends the packet at the 16-bit wrap reliably, `peer.c:207`,
and drops a stale unreliable one, `peer.c:910-912`; the `Conditioner` matches), incoming memory is bounded
(`maximumWaitingData` per peer, `peer.c:956`), the discovery reply can never exceed the query (512 vs at most 342
bytes), `DecodeReply` is strict, and the public headers hold no ENet or platform type and survive `<Windows.h>`
macros and `-Wchanges-meaning`. But a single socket error inside ENet's service closes the whole `UdpTransport`
(F1), which a LAN host will hit in normal play; fix it before tagging `v0.3.0`. F2-F4 are cheap DoS bounds the TCP
transport already has; fix them before tagging too, or document them as known for LAN-only use. F5-F8 are Low.

Findings: 1 High, 3 Medium, 4 Low.

## F1 — High — Any send or receive error on ENet's socket closes the whole `UdpTransport`
`src/Platform/UdpTransport.cpp:309-329` (`Poll`), `docs/transports.md:51`; ENet `protocol.c:1727-1732`
(`enet_protocol_send_outgoing_commands`), `protocol.c:1830-1876` (`enet_host_service`), `win32.c:340-354`,
`win32.c:380-389`, `unix.c:466-473`

Scenario: ENet's `enet_socket_send` returns -1 for any error but `EWOULDBLOCK`/`WSAEWOULDBLOCK`, and
`enet_protocol_send_outgoing_commands` then returns -1 out of `enet_host_service`. One peer's address becomes
unroutable while the others are fine: a client on Wi-Fi drops off and the host's route to it goes (`EHOSTUNREACH`,
`ENETUNREACH`), a VPN or second NIC goes down, the kernel is out of buffers (`ENOBUFS`), or a firewall rule refuses
the destination (`EPERM` on Linux). On Windows the receive side adds `WSAENETRESET` (an ICMP TTL-exceeded) as -1. A
remote can also trigger it: a CONNECT from a spoofed source the host cannot route to makes ENet's `VERIFY_CONNECT`
send fail.
Wrong result: `Poll` raises `Error` (or `ConnectFailed`) for every peer and calls `Close()`, so the whole session ends
for everyone because one address failed once. TCP survives each of these: the error is per socket. The doc line
"A socket failure inside ENet's service (never a lost or reset datagram)" is wrong: a transient send error to one
address is exactly a lost datagram. ENet's send pass also stops at the failing peer, so the peers after it in
`host->peers` get nothing sent that pass.
Fix: treat a -1 from `enet_host_service` as transient: log once, end this `Poll`'s service loop and keep the
transport. Close only if it keeps failing (for example every `Poll` for a second, or a receive-side error that
recurs), since ENet's own peer timeouts already drop a peer that stays unreachable. Correct `docs/transports.md:51`.
Add a test through the `intercept` hook or a fake socket error, if one can be injected.
Status: open

## F2 — Medium — Half-open ENet connects hold every `MaxConnections` slot for about 31 s each
`src/Platform/UdpTransport.cpp:196-242` (`Open`: `enet_host_create(..., MaxConnections, ...)`); ENet
`protocol.c:296-344` (`enet_protocol_handle_connect`), default `duplicatePeers` 4095, default peer timeouts
(limit 32, min 5000, max 30000)

Scenario: a CONNECT datagram puts an ENet peer in `ACKNOWLEDGING_CONNECT`, which takes a slot. The host answers with
`VERIFY_CONNECT` and retries it on ENet's default timeouts (RTO 500 ms doubling), so the slot is held about 31 s
before ENet gives up. `duplicatePeers` stays at 4095, so all 64 can come from one address. These peers never reach
`ENET_EVENT_TYPE_CONNECT`, so `UdpTransport` and the session's 16-handshake trim never see them.
Wrong result: 64 small datagrams every 30 s stop anyone from joining (a full host never answers, so the joiner gets
`ConnectFailed` after 5 s). With spoofed sources the host also reflects about six `VERIFY_CONNECT`s per CONNECT at
the victim. TCP counts and trims these (its 64 cap with the session's 16-handshake trim).
Fix: after each `enet_host_service` loop, walk `host->peers` and cap the peers in `ACKNOWLEDGING_CONNECT`/
`CONNECTION_PENDING` (for example 16, `enet_peer_reset` the oldest), and call `enet_peer_timeout` with a short limit
(`ConnectTimeout`) on them. Set `host->duplicatePeers` to a small number (for example 4) so one address cannot take
every slot.
Status: open

## F3 — Medium — No cap on a peer's outgoing queue
`src/Platform/UdpTransport.cpp:249-294` (`Send`), `docs/transports.md:48`

Scenario: a seated peer acks slowly or not at all, or advertises a tiny window or bandwidth in its CONNECT, and the
game keeps sending reliable packets (snapshots, chat, a world state). ENet keeps every reliable command in
`outgoingSendReliableCommands`/`sentReliableCommands` until it is acked, with no limit. The peer is not timed out
while it acks now and then.
Wrong result: memory grows without bound on the host for as long as that peer stays. TCP drops such a peer at a 4 MB
send queue (`Error`); the UDP transport has no matching cap.
Fix: track the bytes queued per peer (add on `Send`, subtract as ENet frees packets, or read `enet_list_size` and the
packet sizes of the outgoing lists after each flush), and past a limit (4 MB, in `UdpParams`) drop the peer with
`Error` as TCP does.
Status: open

## F4 — Medium — The read budget does not count empty or tiny packets
`src/Platform/UdpTransport.cpp:305-356` (`Poll`: `taken += size`)

Scenario: a connected peer sends zero-length packets. About 170 fit in one datagram, and each adds 0 to `taken`. With
1-byte packets the 256 KB budget allows 256K `Packet`s, each a heap allocation, per `Poll`.
Wrong result: under a sustained flood of empty packets `Poll` loops until ENet is empty, so the budget never applies
and a frame can stall. With tiny packets `packets` grows to hundreds of thousands of entries per frame. TCP's 256 KB
budget counts 4 bytes of frame header per packet, so it cannot be bypassed this way.
Fix: charge a fixed cost per event (for example `size + 64`), or cap the events per `Poll` as well as the bytes.
Status: open

## F5 — Low — ENet's socket keeps `SIO_UDP_CONNRESET` on Windows
`src/Platform/UdpTransport.cpp:221-223` (`Open`); ENet `win32.c:380-389`; `src/Platform/WinSocket.cpp`
(`OpenUdpSocket` turns it off for discovery's sockets)

Scenario: a peer's process exits without a hang-up (a crash), and the host keeps sending to its port until ENet times
it out. Each ICMP port-unreachable makes the next `WSARecvFrom` fail with `WSAECONNRESET`, which ENet reads as "no
more data" and ends that receive pass. This is most likely over `127.0.0.1` and on a LAN.
Wrong result: each such ICMP ends the `Poll`'s reading early, so datagrams from the other peers wait a frame or more,
and a backlog can build for the seconds until the dead peer times out.
Fix: add a `Socket.h` helper (`DisableUdpConnReset(SocketHandle)`, a no-op on POSIX) that runs the same `WSAIoctl` as
`OpenUdpSocket`, and call it on `impl.Host->socket` in `Open` next to `MakeNonInheritable`.
Status: open

## F6 — Low — A failed `enet_peer_send` logs a warning for every packet
`src/Platform/UdpTransport.cpp:287-290` (`Send`); ENet `protocol.c` `handle_connect` (the channel count comes from
the remote's CONNECT)

Scenario: a peer connects with fewer than 3 channels (a non-DingoNet or modified client: ENet accepts any count from
1 up), so every `Send` on channel 1 or 2 fails. The same happens for a peer that ENet has zombied or timed out but
whose disconnect event has not been dispatched yet.
Wrong result: `udp: a packet of N bytes was not queued` is logged for every packet, many times a frame at snapshot
rates, flooding the game's log.
Fix: on `ENET_EVENT_TYPE_CONNECT`, refuse a peer whose `channelCount < CHANNEL_COUNT` (`enet_peer_disconnect_now`,
no `Connected` event), and warn once per peer for other send failures.
Status: open

## F7 — Low — `DecodeQuery` is not strict, and `docs/discovery.md` says it is
`src/LanDiscovery.cpp:98-107` (`DecodeQuery`), `src/LanDiscovery.cpp:236`, `docs/discovery.md:11`,
`docs/discovery.md:14`

Scenario: a query of any size from the reply's size up to 1499 bytes, with any bytes after the protocol field, is
answered.
Wrong result: the docs promise "zero padding to exactly 512 bytes" and "strict decode on both sides" (trailing bytes
dropped and counted as `Malformed()`). The code checks only the header and the `u16`. Amplification is still bounded
by the `size < reply.size()` check, so this is a contract mismatch, but a future discovery version that adds a field
after the protocol cannot rely on version 1 hosts rejecting it.
Fix: require `size == QUERY_SIZE` and all-zero padding in `DecodeQuery`, as the docs say, or change the docs to "at
least as large as the reply; the bytes after the protocol are ignored".
Status: open

## F8 — Low — `LanBrowserParams` timing values are not validated
`src/LanDiscovery.cpp:255-288` (`LanBrowser::Open`), `src/LanDiscovery.cpp:309-324`, `src/LanDiscovery.cpp:369-376`

Scenario: a game passes `QueryInterval` 0 or negative (for example from an unset config value), or NaN.
Wrong result: 0 or negative sends a 512-byte broadcast every `Poll`, 60 or more a second, and every host on the LAN
answers each one (each host's 32-a-frame limit holds, but the LAN sees all of it). NaN makes `now >= m_NextQuery`
false after the first query, so the browser never queries again. A NaN `HostTimeout` never expires a host, and 0
expires every host in the `Poll` after its reply.
Fix: clamp in `Open` as `UdpTransport` does with `UdpParams`: `QueryInterval` to at least 0.1 s, `HostTimeout` to at
least `2 * QueryInterval`, NaN replaced by the defaults, with a warning.
Status: open

## Checked and fine

- Sequenced delivery: ENet sends one packet reliably at the 16-bit wrap (`peer.c:207`) and drops a stale unreliable
  one (`peer.c:910-912`); the `Conditioner`'s per-peer `m_SequencedSent`/`m_SequencedReleased` drop a late packet and
  are erased on disconnect.
- Incoming memory: fragments and waiting data are bounded per peer by `maximumWaitingData` (about 512 KB with the
  defaults); an over-limit packet drops the peer with `Error`.
- `AcquireEnet`/`ReleaseEnet` stay balanced on every `Open` failure path and in `Close`.
- Public headers (`UdpTransport.h`, `LanDiscovery.h`, `Transport.h`): no ENet or platform type, no unqualified
  `min`/`max`, no member named after its own type.
- Discovery amplification: a host answers only a datagram at least as large as its reply (at most 342 bytes vs a
  512-byte query), at most 32 a `Poll`.
- Linux UDP sockets that are not connected ignore ICMP errors; Windows discovery sockets turn `SIO_UDP_CONNRESET` off.
- Minor, not filed: `MakeNonInheritable`'s result is ignored in `Open`; a peer we hung up on keeps its slot past 2 s
  while the remote keeps acking a long queue (`disconnect_later` waits for the queue to empty, and the 2 s
  `enet_peer_timeout` fires only on unacked data), so `docs/transports.md:48` "until its end acks or 2 s pass" is
  approximate.
